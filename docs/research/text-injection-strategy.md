# Research: Text injection strategy — SendInput vs clipboard-paste fallback

Ticket: #11 (M1 ticket 02 — Text injection strategy) · Date: 2026-07-23

## 1. SendInput + KEYEVENTF_UNICODE — mechanics and limits

**How it works.** With `KEYEVENTF_UNICODE`, `wVk` must be 0 and `wScan` carries a UTF-16 code unit. The system synthesizes a `VK_PACKET` keystroke: a `WM_KEYDOWN`/`WM_KEYUP` with `wParam == VK_PACKET` is posted to the *foreground thread's* message queue, and `TranslateMessage` in the target's message loop converts it into `WM_CHAR` carrying the original Unicode character. Microsoft explicitly documents this path as the mechanism for "nonkeyboard-input methods — such as handwriting recognition or voice recognition." ([KEYBDINPUT docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput))

Implications:

- **Foreground-only.** Text goes to whatever thread owns the foreground window at the instant of injection. If focus changes between hotkey release and injection (or the injection itself is slow), text lands in the wrong app. Inject promptly and optionally verify `GetForegroundWindow()` hasn't changed mid-stream.
- **ANSI windows.** `WM_CHAR` is "automatically converted to the appropriate ANSI value if it is posted to an ANSI window" — lossy for characters outside the window's code page ([KEYBDINPUT docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput)). Legacy apps can therefore mangle non-ASCII output; community reports confirm wrong characters in some targets (e.g. [microsoft/terminal#12977](https://github.com/microsoft/terminal/issues/12977), fixed on the terminal side).
- **Surrogate pairs / emoji.** Supported: send each UTF-16 code unit (high then low surrogate) as its own down/up `KEYEVENTF_UNICODE` event. The SendInput remarks note the Windows touch keyboard itself sends supplementary-plane characters this way using the surrogate macros from winnls.h, and that hook listeners must decode them ([SendInput docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), [Surrogates and Supplementary Characters](https://learn.microsoft.com/en-us/windows/win32/Intl/surrogates-and-supplementary-characters)). So in Python: encode to UTF-16-LE, emit one INPUT pair per 16-bit unit. Whether the *target app* renders the emoji is up to the app, but the injection path is well-defined.
- **Modifier state contamination.** `SendInput` "does not reset the keyboard's current state. Any keys that are already pressed when the function is called might interfere" ([SendInput docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)). This matters directly for Cadent: the push-to-talk keys (`Ctrl+Win`) may still be physically held or in transition when injection starts. A held Ctrl turns injected characters into accelerator lookups in many apps. Mitigation: wait for hotkey release (check `GetAsyncKeyState` for VK_CONTROL/VK_LWIN) before injecting, and/or inject key-up events for stuck modifiers first. (Known interaction: Ctrl held + KEYEVENTF_UNICODE behaves inconsistently — [old win32 kernel group thread](https://microsoft.public.win32.programmer.kernel.narkive.com/WAHsxsOT/sendinput-with-keyeventf-unicode-doesn-t-honor-ctrl).)
- **Atomicity and chunking.** Events passed in a single `SendInput` call are inserted "serially" and are "not interspersed with other keyboard or mouse input events" from the user or other injectors ([SendInput docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)). So batching the whole utterance into one call (2 INPUTs per UTF-16 unit) is both fastest and safest against interleaving with real keystrokes. There is no documented hard cap on `cInputs`; practical batches of a few thousand INPUTs are routine (AutoHotkey's SendInput mode sends whole strings in one call). For very long texts, chunk (e.g. 512–1024 chars per call) mainly to bound memory and allow an abort check between chunks; no artificial inter-character delay is required by the API. Some slow/remoted targets (RDP, VMs, some terminals) drop characters when flooded — a configurable per-chunk delay is a useful per-app knob.
- **No per-keystroke pacing guarantee in receivers.** Apps that do their own input throttling/IME processing can still drop events; this is app behavior, not an API limit.

### UIPI (elevated windows)

`SendInput` "is subject to UIPI. Applications are permitted to inject input only into applications that are at an equal or lesser integrity level." Critically: "**This function fails when it is blocked by UIPI. Note that neither GetLastError nor the return value will indicate the failure was caused by UIPI blocking**" ([SendInput docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)). So a non-elevated Cadent injecting into an elevated console/regedit *appears to succeed* (nonzero return) while nothing arrives. The clipboard fallback does not help either — the elevated app never receives the synthetic Ctrl+V. Options: document the limitation; or run Cadent elevated with `uiAccess` (requires signing + install under Program Files) — out of scope for v1. **Detection**: `GetWindowThreadProcessId` + `OpenProcess`/`GetTokenInformation` on the foreground window can determine if it is higher-integrity, letting Cadent warn ("target window is elevated") instead of failing silently.

### Return value semantics (failure detection)

`SendInput` returns the number of events successfully *inserted into the input stream*. Zero means input was blocked (e.g. by another thread's `BlockInput` or UIPI); `GetLastError` gives extended info except in the UIPI case ([SendInput docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)). **A nonzero return does NOT mean the target app consumed the text** — it only means the events entered the system input stream. There is no API-level acknowledgment that characters were accepted.

## 2. App classes that reject or mishandle VK_PACKET input

- **Games using Raw Input / DirectInput / scan codes.** `KEYEVENTF_UNICODE` produces `VK_PACKET` with no meaningful scan code. Games that read scan codes via Raw Input (`WM_INPUT`) or DirectInput never see a real key, so unicode-synthesized input is ignored; the standard workaround in that community is `KEYEVENTF_SCANCODE` injection of real keys, not unicode packets ([GameDev.net thread on SendInput vs DirectInput](https://www.gamedev.net/forums/topic/581515-simulating-keyboard-with-sendinput-api-in-directinput-applications/), [AutoHotkey forum: SendInput in games](https://www.autohotkey.com/boards/viewtopic.php?t=38118)). Additionally anti-cheat systems deliberately filter injected input (low-level hooks see `LLKHF_INJECTED` on all `SendInput`/`keybd_event` events — [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc) / [KBDLLHOOKSTRUCT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-kbdllhookstruct)). **For dictation, games' chat boxes usually use normal WM_CHAR and work; the raw-input gameplay layer doesn't. Treat fullscreen games as "expect failure, use clipboard fallback or skip."** Note `LLKHF_INJECTED` cannot be suppressed from user mode — any app that wants to ignore synthetic input can.
- **Electron / Chromium apps.** Chromium handles `VK_PACKET`/`WM_CHAR` correctly in ordinary text fields — Slack, VS Code, Discord generally accept KEYEVENTF_UNICODE text. Real-world problems are (a) apps that intercept keys via before-input handlers, (b) very fast injection outpacing the renderer IPC (dropped chars), and (c) IME-interaction quirks. These argue for per-app "paced" or "paste" overrides rather than a blanket Electron rule. (Electron itself has no supported API for receiving synthetic keys except `webContents.sendInputEvent` — [electron#8273](https://github.com/electron/electron/issues/8273) — irrelevant to external injection but shows the input path is nonstandard.)
- **Elevated windows** (admin terminals, installers): silently blocked by UIPI as above — the only class where *both* strategies fail.
- **ANSI/legacy apps**: accept input but corrupt non-ASCII (see §1).
- **Terminals**: historically mixed; Windows Terminal fixed its VK_PACKET bug ([#12977](https://github.com/microsoft/terminal/issues/12977)); some third-party terminals/consoles still mishandle unicode packets — per-app override candidates.

**Frequency in practice:** for the PRD's target contexts (browser, IDE, Slack, Word), KEYEVENTF_UNICODE works nearly universally. Fallback demand concentrates in: elevated consoles (unfixable from user mode), games, remote-desktop/VM windows, and a small tail of quirky apps. Expect the override list to stay short.

## 3. Clipboard-paste fallback — mechanics and pitfalls

Sequence: save clipboard → `SetClipboardData(CF_UNICODETEXT)` → inject Ctrl+V via SendInput (scancode/VK, not unicode) → wait → restore clipboard.

Pitfalls, each with primary-source grounding:

1. **OpenClipboard contention.** "OpenClipboard fails if another window has the clipboard open" ([OpenClipboard docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-openclipboard)). Clipboard managers and the clipboard-history service open it frequently. Always retry in a short loop (e.g. 10 × 15 ms) and fail gracefully.
2. **Ownership rules.** Call `OpenClipboard` with a real HWND: "If an application calls OpenClipboard with hwnd set to NULL, EmptyClipboard sets the clipboard owner to NULL; this causes SetClipboardData to fail" ([OpenClipboard docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-openclipboard)). Cadent needs a hidden message-only window for clipboard work.
3. **Saving/restoring non-text formats is hard.** A full-fidelity save requires enumerating every format and copying every `HGLOBAL` — but many formats are **delayed-rendered** (owner renders on demand), so "saving" them forces rendering (potentially huge, e.g. Excel ranges) or loses them. Restoring only `CF_UNICODETEXT`/`CF_TEXT` silently destroys rich content (files copied in Explorer, images, RTF). Delayed-render requests can also time out (~30 s) and drop data ([Clipboard Operations / delayed rendering](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-operations), [community report of history losing delayed-rendered items](https://windowsforum.com/threads/why-windows-11-clipboard-history-misses-items-and-how-to-fix-it.395755/)). **Practical policy: restore text-family formats faithfully; for non-text clipboard content, either skip restore-and-notify or restore best-effort — and rely on Win+V history as the user's real safety net.**
4. **Timing before restore.** Ctrl+V is asynchronous: the target processes `WM_PASTE`/accelerator on its own schedule and reads the clipboard *then*. Restoring too early pastes the *old* clipboard. There is no completion signal; robust implementations wait a delay (100–300 ms typical; per-app tunable) or watch `GetClipboardSequenceNumber()` ([GetClipboardSequenceNumber docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipboardsequencenumber)) — though sequence number changes on *write*, not read, so it detects interference, not paste completion. Some apps with delayed paste handling (terminals prompting on multi-line paste, remote sessions) need longer delays.
5. **Clipboard history (Win+V) and cloud sync pollution.** Every transient `SetClipboardData` lands in the user's clipboard history and can sync across devices — a privacy problem for a dictation app. Windows provides registered formats to opt out: place **`ExcludeClipboardContentFromMonitorProcessing`** (any data) to keep the item out of history *and* cloud sync; `CanIncludeInClipboardHistory`=0 and `CanUploadToCloudClipboard`=0 give finer control ([Clipboard Formats — Cloud Clipboard and Clipboard History Formats](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats)). Caveat: excluding from monitor processing also hides the injected text from third-party clipboard managers (good) — but note some managers ignore these formats. **However**, PRD 6 wants "transcript in clipboard as last resort" on failure — in *that* path, deliberately do NOT exclude from history.
6. **Clipboard-manager interference.** Managers that immediately re-open/re-write the clipboard can race the save→set→paste→restore window (see #1, #4). The sequence-number check before restore avoids clobbering something the user (or a manager) put there mid-flight: if the sequence number is not the one from our own `SetClipboardData`, skip the restore.
7. **Paste interception.** Apps that remap Ctrl+V (some terminals use Ctrl+Shift+V; vim uses different registers; some remote apps forward it) need a per-app configurable paste chord.
8. **UIPI again.** The synthetic Ctrl+V is still SendInput — clipboard fallback does not penetrate elevated windows.

## 4. Failure detection — can fallback be automatic?

- **API level: no.** Nonzero `SendInput` return ≠ text accepted; UIPI failures are explicitly indistinguishable from success ([SendInput docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)).
- **Pre-flight elevation check: yes.** Detect a higher-integrity foreground window before injecting (token integrity level of foreground PID) and warn/skip — cheap and reliable.
- **Read-back verification: partial.** UI Automation (`TextPattern`/`ValuePattern`) on the focused element can confirm the text appeared, but coverage is inconsistent (many apps expose no patterns; terminals/games none), it adds latency, and false negatives would cause double-insertion if used to auto-retry via paste. Not recommended for v1 auto-fallback; usable later as an opt-in "verify" mode that only *notifies* on suspected failure.
- **Conclusion: the per-app override list (PRD 5.4) must drive strategy selection.** Automatic fallback should be limited to the two detectable cases: `SendInput` returning less than the event count / zero (retry via clipboard), and elevated-foreground pre-flight (notify, don't attempt). Everything else is configuration.

## 5. Recommendation

1. **Default: SendInput + KEYEVENTF_UNICODE**, whole utterance batched in one call (2 INPUT structs per UTF-16 code unit, surrogates as consecutive units), after (a) waiting for the hotkey modifiers to be physically released (`GetAsyncKeyState`) and (b) verifying the foreground window is unchanged and not higher-integrity.
2. **Fallback: clipboard-paste**, triggered by (a) per-app override match, (b) `SendInput` returning fewer events than sent, (c) user-initiated "retry as paste" affordance. Implementation: hidden window owner; OpenClipboard retry loop; set `CF_UNICODETEXT` + `ExcludeClipboardContentFromMonitorProcessing`; send Ctrl+V by virtual-key/scancode; wait per-app delay (default ~150 ms); check `GetClipboardSequenceNumber` before restoring; restore text formats only, skip-and-log otherwise.
3. **Last resort (PRD 6 reliability):** on any injection failure, leave the transcript on the clipboard *without* the exclusion format and toast "copied to clipboard — press Ctrl+V", plus history entry.
4. **Per-app override config must express:** match key (process exe name; optionally window-class), strategy (`sendinput` | `clipboard` | `clipboard-no-restore` | `notify-only`), inter-chunk delay ms and chunk size (for slow SendInput targets), paste chord (default `ctrl+v`, e.g. `ctrl+shift+v` for terminals), paste-settle delay ms, and restore-clipboard bool. Ship defaults: elevated windows → notify-only; known terminals → clipboard with `ctrl+shift+v`; fullscreen/game processes → clipboard or notify-only.
